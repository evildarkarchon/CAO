# #459 Keep GPU BC7 encoding with the directxtex crate [CLOSED]

## Question

How do we keep GPU BC7 encoding when the texture optimizer moves to the `directxtex` Rust crate?

Today `src/TexturesOptimizer.cpp` creates a D3D11 device (`createDevice`, about lines 44-109; feature levels 11_0, 10_1, and 10_0) and encodes BC6H/BC7 with DirectXTex's GPU `Compress(device, …, TEX_COMPRESS_BC7_USE_3SUBSETS, 1.f)`. It falls back to the CPU when no device is available. All other formats use the CPU `Compress`. The `directxtex` crate (Ryan-rsm-McKenzie, 1.3.x) appears to bind only the CPU paths. `ba2` already depends on it.

Compare these options and recommend one:

- Extend or fork `directxtex-rs` to bind the D3D11 `Compress` overload. Report the effort and the build implications: does the crate build DirectXTex with DX11 support?
- Write a small C++ shim crate for the GPU path next to the `directxtex` crate.
- Use CPU-only ISPC BC7 (`intel_tex_2`) or the `directxtex` crate's CPU BC7. Report the quality and throughput relative to DirectXTex GPU BC7, and whether output would still count as "equivalent".

Also confirm that the crate covers every other DirectXTex call CAO makes: TGA and DDS load, `MakeTypelessUNORM`, decompress, resize with `TEX_FILTER_SEPARATE_ALPHA | TEX_FILTER_FORCE_NON_WIC`, `GenerateMipMaps`, `Convert`, `SaveToDDSFile`, `IsCompressed`, `HasAlpha`, `IsCubemap`, and `GetAlphaMode`.

## Resolution

**Recommendation: option A.** Fork `directxtex-rs`, bind the D3D11 `Compress` overload, and patch the fork in for the whole workspace.

- **Fork changes.** In `build.rs`, also compile `BCDirectCompute.cpp` and `DirectXTexCompressGPU.cpp` on Windows, and vendor the 14 `fxc`-generated shader `.inc` files (upstream's `USE_PREBUILT_SHADERS` model). Add one `extern "C"` wrapper and an `unsafe fn compress_gpu(device: *mut c_void, …)`. That is about 100 hand-written lines, or roughly 1–2 days.
- **Wiring.** Add `[patch.crates-io] directxtex = { git = <fork> }` so `ba2` (which requires `directxtex = "1.1.0"`) links the same single copy of DirectXTex.
- **Device and fallback.** Create the device in Rust with the `windows` crate, mirroring `createDevice`. Fall back to the crate's existing CPU `compress`, as C++ does today.
- **Optional fork extras.** Bump the DirectXTex submodule to `may2026` to match the C++ oracle's vcpkg build. Add `Send` for `ScratchImage`. Offer the change upstream as an answer to directxtex-rs#3.
- **Option B (separate shim crate): rejected.** The GPU sources need `DirectX::Internal::*Scanline` and other internals from inside the crate's native library. Option B is the same work as A plus fragile cross-crate linking, or duplicate C++ symbols in one link.
- **Option C (CPU-only): rejected.** The crate's CPU BC7 is single-threaded: it is built without OpenMP, so `TEX_COMPRESS_PARALLEL` returns `E_NOTIMPL`. Upstream itself calls it "quite slow", so it fails the "no meaningful regression" bar. `intel_tex_2` is fast but a different engine, which breaks "same native engines". Its output could only be "equivalent" under a PSNR rule.

## Key facts

- **The crate has no GPU path today.** `directxtex` 1.3.0 (2025-01-08, still latest) vendors DirectXTex `oct2024` (`9260384a`). Its `build.rs` skips `BCDirectCompute.cpp`, `DirectXTexCompressGPU.cpp`, and `DirectXTexD3D11.cpp`. It ships no shaders, and its FFI has no `ID3D11Device` entry. On Windows, `DirectXTex.h` already includes `<d3d11_1.h>`, so the GPU declarations are visible to the crate's FFI compile.
- **Upstream does not commit compiled shaders.** `CompileShaders.cmd` generates them with `fxc.exe`. I compiled all 14 locally with SDK 10.0.26100 `fxc`: 0 failures, 17.5 s, 3.47 MB.
- **Upstream is dormant.** directxtex-rs#3 ("GPU support", 2025-07) has no reply, and the OpenMP PR #4 is unmerged.
- **API coverage.** The crate covers every other call CAO makes: TGA and DDS load (memory APIs plus `std::fs`), `IsTypeless`, `MakeTypelessUNORM`, `OverrideFormat`, `Decompress`, `Resize` (both flags), `ScratchImage::Initialize`, `GenerateMipMaps`, `Convert`, CPU `Compress`, `SaveToDDSMemory` (same `EncodeDDSHeader` as `SaveToDDSFile`), `IsCompressed`, `HasAlpha`, `IsCubemap`, and `GetAlphaMode`.
- **One gap.** `CopyRectangle` is bound, but `ScratchImage` has no `&mut Image` accessor. Building the destination `Image` from public fields works around it.
- **No-op flag.** C++ ORs `TEX_FILTER_SEPARATE_ALPHA` into the CPU `Compress` flags. This does nothing (upstream's `GetBCFlags` masks it off), so Rust passes `TEX_COMPRESS_DEFAULT`.

## Facts for other tickets

- **#467 output equivalence.** C++ BC7 output already depends on hardware: the GPU path (with `BC7_USE_3SUBSETS`) and the CPU fallback (without it) are different encoders. BC7 equivalence therefore has to decode and compare (`Image::compute_mse` is bound) plus compare metadata. The BC7 codec and shader changes between `oct2024` and `may2026` appear to be formatting only.
- **#468 workspace architecture.** `ScratchImage`, `Image`, and `Blob` are not `Send`. The worker must call `CoInitializeEx`, because `GenerateMipMaps` without `FORCE_NON_WIC` can use WIC. Keep one D3D11 device per thread, since DirectXTex uses the immediate context. Add the `windows` crate. DirectXTex is built by `cc`, with no CMake or vcpkg.
- **#461 ba2.** The fork must stay 1.x so the patch applies to `ba2`. `ba2` uses `load_dds` and `encode_dds_header` from the same copy.

## Open risks

- CAO owns a fork.
- The GPU binding was not built in this spike; only the shader compile was verified.
- GPU BC7 determinism across drivers is unverified, which is moot under a decode-and-compare rule.
- Forgetting COM init breaks mipmaps on the WIC path.
