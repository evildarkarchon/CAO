# #472 Decide how the harness runs both builds and compares their facts [CLOSED]

## Question

How does the differential harness run the C++ oracle and the Rust driver on one corpus case, and turn each side's output into the normalised fact model that "Define equivalent output per Asset Kind" compares?

Decide:

- **The oracle build.** How it is built: the `CAO_BUILD_GUI=OFF` CLI, with vcpkg DirectXTex pinned to `may2026`. Then where it lives, and how the harness locates it.
- **Per-case isolation.** Each build runs in its own copy of the case tree and its own copy of `profiles/`, with the oracle's working directory set to its exe folder. How is that laid out, and how are runs that write to a Mod Root kept apart?
- **Options the oracle can't reach.** The oracle's CLI can't set archive options: compression, dummies, merging Incompressible or textures, and deleting sources all take their defaults (`src/OptionsCAO.h:42-47`, `src/Run/ApplicationRunWork.cpp:136-145`). Are non-default archive options covered by Rust tests only, or does the oracle get a way to set them?
- **What `cao-parity` emits.** It is a headless binary over the `cao-optimizers` composition root. Decide its output format, and how the oracle's `EVENT:` stream plus exit code and `cao-parity`'s output are each parsed into the same fact model.
- **Mapping C++ codes to Rust types.** How C++ `RunFailureCode` and `SkipReason` integers map onto the Rust enums.
- **BC7 threshold calibration.** Where and when the one-off calibration of the 40 dB BC7/BC6H threshold runs (the oracle against itself, GPU against CPU-forced).
- **How the harness is invoked and reports.** A `cargo test` target, a separate command, or both? Since the oracle needs a GPU and the C++ toolchain, decide what runs where and how a Different verdict is reported for diagnosis.

## Resolution

`cao-parity` is one binary that both drives the Rust side and runs the harness. It runs a small, modified C++ CLI oracle and the Rust driver on isolated copies of each case. It turns both sides into one raw `RunFacts` type, normalises both with the same code, and compares them under the rules in "Define equivalent output per Asset Kind".

### The oracle build

- **Build.** A Release build of the `CAO_BUILD_GUI=OFF` CLI (target `Cathedral_Assets_Optimizer`), configured from the `vs2026-windows` preset into `build/oracle` with `-DCAO_BUILD_GUI=OFF -DBUILD_TESTING=OFF`.
  - It needs its own binary dir, because the GUI build produces the same target name.
  - Qt is linked statically, so the exe needs only the system CRT. Build Release, because the Debug CRT exists only on machines with VS installed.
  - The command is documented. The harness never drives CMake.
- **DirectXTex pin.** The vcpkg baseline already resolves DirectXTex to `may2026` (`2026-05-07`), but nothing pins it. Add one `overrides` entry, `{"name":"directxtex","version-date":"2026-05-07"}`, to `vcpkg.json`. An overlay port is not needed.
- **Locating it.** The harness takes `--oracle <exe>` or `CAO_ORACLE`. There is no auto-discovery.
- **`hkxcmd.exe`.** Looked up from `--hkxcmd`, then `CAO_HKXCMD`, then `<workspace root>/bin/hkxcmd.exe`, the distributed layout. The workspace copy stays gitignored and uncommitted: it is a 10 MB third-party binary from 2012 with an unclear redistribution licence. The harness copies the one resolved binary into both sides of every case. Without it, cases that request animations are reported as **not run**, never as passing.

### Oracle-only C++ changes

These are allowed as one small change that is deleted with the C++ tree. `docs/cli.md` is updated to match.

1. **Archive options.** Five CLI flags, in `src/OptionsCAO.cpp`, for compress, dummies, merge Incompressible, merge textures, and delete sources. Today the CLI never assigns these and never reads `settings.ini`, so they always take the defaults in `src/OptionsCAO.h:42-47`. The generator still never merges textures for FO4, which is a deviation trigger.
2. **Escaping.** The event renderer (`src/CliRun.cpp`) escapes `\`, `|`, CR and LF in free-text fields (detail, message, service detail). Today an `Asset Failure` line's `affectedPath` sits between two unescaped free-text fields, and the terminal event spans several lines with no prefix.
3. **Forcing CPU BC7.** An environment variable (for example `CAO_ORACLE_FORCE_CPU_BC`), checked in `createDevice`, makes device creation fail so that BC6H/BC7 take the CPU path. It is used only by calibration. Nothing can force the CPU path today.

### The fact pipeline

- **One raw `RunFacts` type** in `cao-parity`.
- **Oracle side.**
  - Parsed from stdout plus the exit code.
  - The parser reads until the process exits, not until the terminal event, because late diagnostics can follow it.
  - stderr is captured for the report but not parsed. The CLI prints a Qt warning for the commented-out `bo` option.
  - The grammar is strict once escaping exists.
- **Rust side.** `cao-parity run` builds `RunFacts` in-process from the typed Run Events and the final Run Evidence, and writes it as JSON to `--facts <path>`. The `EVENT:` text format is not revived.
- **One shared normaliser** applies to both sides. It handles the Run ID, nonces and sequence numbers, and makes paths relative to each side's case root. Then the comparator runs. Neither side normalises on its own.
- **Exit code.**
  - The comparator checks Run Outcome and Start Error, not the exit code.
  - The oracle parser checks that the exit code is **consistent** with the oracle's own Outcome line (0/1/2/130). A mismatch is a harness error.
  - `cao-parity run` exits 0 whenever it produced facts, whatever the Run Outcome. It exits non-zero only on a driver error or crash.
- **Mapping C++ codes to Rust types.**
  - The oracle parser holds hand-written, exhaustive `match` tables:
    - `RunFailureCode` 0–18;
    - `SkipReason` 0–2;
    - `StartError` 0–2;
    - the **names** of Run Phases, Run Outcomes, Phase Skip Reasons and mutation kinds.
  - An unknown integer or name is a **harness error**, never a Different verdict.
  - Rust domain enums carry no `#[repr]` or discriminants tied to the C++ order.
  - Unit tests pin each table against captured oracle transcripts.

### Per-case isolation

```
<work>/<case-id>/          <work> defaults to target/parity/
  case.json                the CaseSpec (see below)
  input/                   pristine tree: reference for files neither build touched
  oracle/                  oracle working directory
    profiles/  bin/hkxcmd.exe  logs/
    <case tree, same Mod Root names>
  rust/                    cao-parity run --app-dir
    profiles/  bin/hkxcmd.exe  logs/
    <case tree, same Mod Root names>
  report.md                only for a case with a Different verdict or a harness error
```

- **Same names.** Mod Root folder names (and the Several Mods parent) are identical on both sides, because Archive and plugin names derive from them.
- **Same volume.** Both sides sit on the same volume, for staging, durable rename and the capacity probes.
- **Private profiles.** Each side has its own `profiles/`. `Profiles::loadProfile` writes `profile=` into `common.ini`.
- **Oracle working directory.** The oracle's working directory is its per-case `oracle/` dir, **not its exe folder**. The exe stays in `build/oracle`. `profiles/`, `bin/hkxcmd.exe`, `logs/` and `translations/` all resolve against the working directory in C++. This amends the map's Transition note.
- **Rust app dir.** The composition root takes the **app directory** as a parameter, used for `profiles/`, `logs/` and `bin/`. `cao-gui` passes `current_exe().parent()`, and `cao-parity run` passes `--app-dir`. The "relative to the exe" rule therefore lives only in `cao-gui`'s `main`.
- **Cleanup.** Passing cases are deleted. Failing ones are kept.

### The case spec

- Each case has a `case.json`, which deserialises into a `CaseSpec`. It holds the profile, `om` or `sm`, Dry Run, requested work, texture options, mesh level, headparts and resave, archive extract/create/delete-backup, and the five archive options.
- **The harness alone renders a spec into oracle argv.** A spec the oracle cannot express is a harness error at render time, never a silent default.
- **`cao-parity run` reads the same file** and fills `cao-profiles`' options model from it, the model the GUI fills from its widgets. It then hands that model to the composition root, which translates it into the Run Request and per-run settings. This mirrors the oracle's `OptionsSnapshot` and `makeApplicationRunRequest`, so validation and profile-forced defaults are compared too. `RunRequest` is never built directly.
- How specs are produced (the parameter space and hand-written seeds) is left to "Decide what the differential corpus generator produces". This ticket fixes only the shape.

### Invocation and reporting

- **`cao-parity` subcommands:**
  - `run`: the driver. The harness spawns it once per case.
  - `corpus`: generate cases, run both sides, compare, and report.
  - `case <id>`: replay one case.
  - `calibrate`: see below.
- **`cargo test -p cao-parity`** covers only the parser, the normaliser, the comparator, and the mapping tables, using captured oracle transcripts and small fixture trees. It never needs the oracle, a GPU or the C++ toolchain.
- **Where it runs.** Locally, on a Windows dev machine with a GPU. There is no CI today, and none is added.
- **Run order.** Cases run sequentially, and within a case the oracle runs before the Rust driver. There is a per-case timeout; a timeout is a harness error.
- **Console summary.** Identical, Equivalent and Different counts per Asset Kind, plus harness errors and cases not run.
- **`report.md`** for each Different contains:
  - the fact-model diff;
  - each failing artifact and the rule it broke (for BC7/BC6H, the PSNR per mip and face);
  - both stdout/stderr captures and both HTML logs;
  - the exact replay command with its seed.

### BC7 threshold calibration

- **How it runs.** `cao-parity calibrate` runs the BC7/BC6H corpus cases through the oracle twice, once on the GPU and once with CPU forced through the new environment variable. It records the lowest PSNR it observes, per format.
- **The threshold** stays at **40 dB**, unless the observed floor is lower; then it becomes the floor minus 1 dB.
- **Recording.** The value, and the host and driver it was measured on, are committed as a constant with a comment.
- **When.**
  - Once, when the corpus first passes.
  - Again by hand only after a DirectXTex bump, or if BC7 verdicts cluster near the threshold.
- **Expectation.** GPU against GPU on one driver is probably Identical. The threshold mainly guards a side that has fallen back to CPU.

### Not glossary or ADR material

These are verification mechanics, not CAO's domain, so `GLOSSARY.md` is unchanged. No decision here meets the ADR bar: the oracle changes are deleted with the C++ tree, and the rest is internal to `cao-parity`.
