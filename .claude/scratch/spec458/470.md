# #470 Replace plog with a log-facade HTML sink [CLOSED]

## Question

How should the binary's logging sink replace plog behind the `log` facade?

[Choose the Rust workspace crates and seams](https://github.com/evildarkarchon/CAO/issues/468) settled that libraries log only through `log` macros, hold no logger state, and leave the binary to install the sink. Decide:

- **HTML file format.** Keep the current HTML log location and format (a map-level compatibility rule). Which parts of plog's output must survive: header, line layout, severity markup, and timestamps?
- **Rotation.** What rotation policy does plog apply today, and does the port keep it unchanged?
- **Per-run redirect.** C++ redirects logging for each GUI run (`applyRunLogging`, `MainWindow.cpp:266`). How does a global `log` sink switch files safely while a Run Worker is logging?
- **GUI feed.** How does the sink hand the Log tab `{text, severity}` lines (debug, info, warning, error, run detail), and on which thread? The main-window prototype settled the coloured rows. The GUI must not parse HTML.
- **Hand-written or crate-based.** Is the sink a small hand-written `log::Log` implementation, or built on an existing crate?
- **Home.** Where does the sink live: a module in `cao-gui` or a separate crate (`cao-parity` may want the same file format)?


--- comment by evildarkarchon
## Resolution

**Answer:** write a hand-written `log::Log` sink of about 200 lines, as a module beside the composition root in `cao-optimizers`. It formats each accepted record once. The HTML line goes to the Application Log file, and a plain `{severity, text}` row goes to an optional, Slint-agnostic subscriber. It keeps plog's file format, rotation and redirect timing, except for the deviations listed below. The human accepted every recommendation over three grilling rounds.

### Facts it rests on (C++ today)

- The path is `<cwd>/logs/<profile>/yy.MM.dd.hh.mm.html`, stamped when a profile loads (`Profiles.cpp:44`). All runs in a session for that profile append to it.
- plog 1.1.11 (`ApplicationLogging.cpp`, `Logger.h`) writes a UTF-8 BOM and a `<style>` header only into an empty file. Each record is `<br><font color=X>…</font>`, with no newline and no HTML escaping.
  - Info layout: `YYYY-MM-DD HH:MM:SS [SEV] msg`.
  - Debug layout: `YYYY-MM-DD HH:MM:SS.mmm SEV   {Func@line} msg`, with the severity left-padded to 5 characters.
- Rotation: when the file passes 250,000 bytes (checked before each write), it shifts to `name.1.html` … `name.999.html`, keeping 1,000 files. The live file keeps the base name.
- The logger bootstraps in `main` and is redirected only at run start (`applyRunLogging`, `MainWindow.cpp:266`), after `saveUi`.
- The Log tab rereads the whole file, calls `appendHtml`, then appends the `GuiRun.cpp` run-detail strings. Those strings are never written to the file.
- Severity use: 27 error, 21 verbose, 13 info, 4 warning, 1 debug, 1 fatal (bootstrap `displayError` only).

### Decisions

1. **File format.** Keep plog's bytes:
   - BOM and `<style>` header only into an empty file.
   - `<br><font color=…>` per record, with the same colour table (ERROR Red, WARN Orange, INFO Green, DEBUG Blue, VERB Purple).
   - The same two timestamp layouts (milliseconds in debug only) and the same severity tokens.
   - Mapping from plog: `verbose` → `trace!`, still printed as `VERB`; `debug` → `debug!`.
   - Forced and fixed changes are on the deviation list.
2. **Rotation.** Unchanged: a 250,000-byte threshold checked before each write, up to 1,000 files, `name.N.html` shift order, and a fresh BOM and header in each new file. Only files that exist are renamed, which isn't observable.
3. **File naming.** `cao-gui` owns profile selection, so it stamps the `yy.MM.dd.hh.mm` path when a profile is selected, exe-relative per the existing deviation. All runs in that profile session append to it. Re-selecting a profile stamps a new name. Two launches in one minute share a file, and the header isn't repeated.
4. **Redirect.** Bootstrap in `main` with the startup profile's path and level, then redirect at each run start. A redirect takes the sink's single lock, swaps the handle, path, layout and max level, then calls `log::set_max_level` (Trace when debug logging is on, Info when it's off). One handle is used, with the layout chosen per record. The Run Lock means no Run Worker is logging during a redirect, and the lock makes it safe regardless.
5. **Log tab feed.**
   - The sink emits plain `{severity, text}` rows: the file line without markup (timestamp, severity, and the debug location). Records filtered out by level appear in neither the file nor the tab.
   - Hand-off: rows go into a `Mutex<Vec<LogLine>>`, and one `slint::invoke_from_event_loop` is scheduled only when that buffer goes from empty to non-empty. The UI thread drains it into the `VecModel`.
   - The tab mirrors the current Application Log for the session. It clears when a redirect changes the path. Run-detail rows (`GuiRun.cpp` strings, prototype "detail" style) stay pinned below the log rows.
6. **Row cap.** The tab keeps the most recent 10,000 log rows, dropping the oldest. Run-detail rows are never dropped. The full history stays in the file through "Open log file".
7. **Startup replay.** The sink keeps the session's rows in that capped buffer from bootstrap onward. Attaching a subscriber replays them, and a redirect to a new path clears the buffer.
8. **Hand-written.** No crate fits: `log4rs` has no "header on new file" hook, `flexi_logger` uses its own naming, and `fern` has no rotation.
   - Dependencies are `log` and `chrono`.
   - Writes are unbuffered, one write per record as plog does, so "Open log file" mid-run is current and a crash loses nothing.
   - A poisoned lock is recovered with `into_inner`, and `log()` never panics.
9. **Time source.** `chrono` with `default-features = false, features = ["clock", "std"]`, shared by the sink and `cao-gui`'s file stamp.
10. **I/O failures.** Keep C++'s three scopes:
    - Bootstrap returns a typed error. `main` shows a critical box and exits 1.
    - Redirect returns a typed error. The GUI shows "The log file for this run could not be opened: …" and doesn't start the run.
    - Per-record write and roll failures are swallowed, and the subscriber still gets the row.
    - Opening creates `logs/<profile>/` first.
11. **Run-detail rows stay GUI-only**, as today. Writing them to the file would be a feature.
12. **Home.** A module beside the composition root in `cao-optimizers`, so `cao-parity` writes its log through the same code without depending on Slint. The subscriber hook is `Box<dyn Fn(&[LogLine]) + Send + Sync>`, and `cao-gui` adapts it to Slint. A few golden tests in `cao-optimizers/tests/` pin the format, as "Define equivalent output per Asset Kind" requires.

### Deviations (added to the map's list)

- The debug layout shows `{module::path@line}` instead of `{Func@line}`. This is forced: `log::Record` has no function name.
- `fatal` is written as `ERROR`. This is forced: `log` has no fatal level, and only the bootstrap error box used it.
- Message text is HTML-escaped (`& < >`).
- Each record ends with `\n`. Browsers don't show it, and the file becomes one record per line.
- Toggling debug logging between runs no longer silently drops the log. In C++, the two plog appenders each open the file with `_SH_DENYWR`, so the newly selected one can't open it.
- The Log tab is no longer truncated to the current rotation chunk, and it shows startup records before the first run.

### Domain

Added **Application Log** to `GLOSSARY.md`: the per-profile record, written for people, of what CAO did across a session's runs. It is never Run Evidence, and no Run Outcome depends on it. No ADR, because none of these decisions is hard to reverse.
