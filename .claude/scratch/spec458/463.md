# #463 Map the Windows file-safety primitives to Rust [CLOSED]

## Question

How does each Windows file-safety primitive in CAO's staged-publication and run code map to Rust: `std`, `std::os::windows`, or the `windows` / `windows-sys` crate?

The crash-safety guarantees in `docs/architecture/staging-ownership.md` rest on native calls in these files:

- `src/Run/NativeFilePins.*`
- `src/Run/NativeVolume.h`
- `src/Run/TemporaryArtifactRegistry.cpp`
- `src/Run/StagingRecovery.cpp`
- `src/AssetExecution/AssetExecutor.cpp`
- `src/Run/ArchiveExtraction.cpp`
- `src/Run/ArchiveFinalizationLoadingPlugins.cpp`
- `src/Run/ArchivePathComparison.h`

Inventory every primitive, then map each one to a Rust equivalent and note any semantic gaps. The inventory should include:

- `CreateFileW` with restricted share modes and `FILE_FLAG_WRITE_THROUGH`, pinning sources and ancestor directories.
- Reparse-point rejection.
- `GetFileInformationByHandle(Ex)` with `FileBasicInfo`, `FileIdInfo`, and `FileAttributeTagInfo`.
- `SetFileInformationByHandle` with `FileRenameInfo` (replace and no-replace) and `FileDispositionInfo`.
- `FlushFileBuffers`.
- `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`.
- `GetVolumePathNameW` and `GetVolumeNameForVolumeMountPointW`.
- `CompareStringOrdinal`.
- The `owner.lock` exclusive handle.

Identify which mappings `std` covers. For example, `OpenOptionsExt::share_mode` and `custom_flags` cover `CreateFileW` share modes and flags. Identify which need `windows-sys` and which helper crates are trustworthy (for example `same-file`, `fs4`, `dunce`). Recommend a crate set.

Also recommend how to resolve the exe directory robustly, since the port resolves paths relative to the exe. Cover `current_exe`, canonicalization, and the `\\?\` prefix.

## Resolution

Each primitive maps cleanly. **Open handles with `std`, and query or mutate them with `windows-sys` on `file.as_raw_handle()`.** The full inventory has 23 rows, each with C++ call sites and the semantic gaps; it is in the research note linked at the end. All of it was checked against Rust std 1.99 source, MSVC STL 14.51, the crate sources, and Microsoft Learn.

### Primitive → Rust

| Primitive | Rust | Notes |
|---|---|---|
| `CreateFileW` pins: directory, source, plugin, cleanup, staged-publish (restricted share modes, `BACKUP_SEMANTICS`, `OPEN_REPARSE_POINT`, `WRITE_THROUGH`) | `OpenOptions` + `OpenOptionsExt::{access_mode, share_mode, custom_flags}` | Full coverage. std also adds `\\?\` to long paths. **Always pass `share_mode`**: std defaults to `READ\|WRITE\|DELETE`. |
| `owner.lock` (`GENERIC_READ`, share 0, `CREATE_NEW`/`OPEN_EXISTING`) | Same, mapping raw OS error 32/33 to `StagingActive` | **Do not use `File::lock`.** It is `LockFileEx`, not share-mode exclusion. **Trap:** `create_new(true)` errors unless `.write(true)` is also set, even when `access_mode` is set (std source). Use `.write(true).access_mode(GENERIC_READ).share_mode(0).create_new(true)`. |
| Reparse-point rejection | `metadata().file_attributes() & FILE_ATTRIBUTE_REPARSE_POINT` (stable) | **Not `is_symlink()`.** It only flags name-surrogate tags (symlink, junction), so other reparse points would pass. |
| `GetFileInformationByHandle` (volume serial, file index, link count) | `windows-sys` | The std accessors are unstable (`windows_by_handle`). |
| `…Ex(FileBasicInfo)` change time, `…Ex(FileIdInfo)` 128-bit ID + 64-bit fallback, `…Ex(FileAttributeTagInfo)` | `windows-sys` | `change_time` is unstable in std and always `None` on desktop Windows. |
| `SetFileInformationByHandle(FileRenameInfo)` Replace/NoReplace, absolute name | `windows-sys`, with a hand-built zeroed, aligned `FILE_RENAME_INFO` buffer | No public std API. Keep `FileRenameInfo`, not the POSIX `…Ex` form. |
| `SetFileInformationByHandle(FileDispositionInfo)` | `windows-sys` | `std::fs::remove_file` is path-based `DeleteFileW`, so it is not identity-bound. |
| `FlushFileBuffers` | `File::sync_all()` | Exactly the same call. The handle needs `GENERIC_WRITE`. |
| `MoveFileExW(REPLACE_EXISTING \| WRITE_THROUGH)` | `windows-sys` | `std::fs::rename` drops `WRITE_THROUGH`. |
| `GetVolumePathNameW` growing buffer, `GetVolumeNameForVolumeMountPointW` | `windows-sys`, porting `NativeVolume.h` line for line | No std API |
| `CompareStringOrdinal(…, TRUE)` | `windows-sys` `Win32_Globalization`, wrapped in an `Ord` newtype | No pure-Rust equivalent. Rust case mapping can expand characters (ß → SS). |
| Also: `hard_link_count`, `filesystem::space`, `random_device` nonces | `windows-sys` link count; `GetDiskFreeSpaceExW`; `getrandom` | |

### Recommended crate set

```toml
windows-sys = { version = "0.61", features = ["Win32_Foundation", "Win32_Security", "Win32_Storage_FileSystem", "Win32_Globalization"] }
getrandom = "0.3"
dunce = "1"   # exe dir / display paths only
```

- **Reject `same-file`.** It uses 64-bit IDs only, with no `FileIdInfo`, and it follows reparse points.
- **Reject `fs4`.** Its locks are `LockFileEx`, and its `statvfs` uses a fixed 261-unit `GetVolumePathNameW` buffer, which fails on the deep mounted folders that `NativeVolume.h` handles.
- **Skip the `windows` crate** for this layer.
- **Put all `unsafe` and `windows-sys` code in one small crate** (e.g. `cao-winfs`).

### Exe directory

- Call `std::env::current_exe()` (`GetModuleFileNameW` with a growing buffer) and take `.parent()`.
- **Do not canonicalize.** That would send a symlinked or junctioned install to the link target's `profiles/`.
- Apply `dunce::simplified`, because a `\\?\` base treats `/` literally.
- Join one component at a time, never call `set_current_dir`, and resolve once at startup.

### Semantic gaps and risks

- **Manifest root text (critical).** `CAO-STAGING` stores `generic_u8string(fs::canonical(root))`, and recovery compares it byte for byte (`StagingRecovery.cpp:288`). MSVC `canonical` always strips `\\?\X:`, maps `\\?\UNC\` to `\\`, and falls back to `\\?\GLOBALROOT` + NT path. `std::fs::canonicalize` keeps the prefixes and fails where MSVC falls back. `dunce` keeps `\\?\` past 260 chars and never strips UNC. **The port needs an `msvc_canonical` helper:** `GetFinalPathNameByHandleW` plus the same rewrites, and a matching `weakly_canonical`. Without it, C++-written manifests fail recovery as `StagingOwnershipUnverified`.
- **Manifest embedding (#468).** Embed the same manifest as C++: `longPathAware` + `activeCodePage` UTF-8. Raw path-taking Win32 calls depend on it, and so do the narrow-path C++ engines.
- **Not verified live:** canonical text for a volume with no drive letter and for a mapped network drive. Add both to the differential corpus.
- **Mapped archives:** `ba2` can read straight from the pinned `File` (`Reader<&File>` + `memmap2`), which improves on the C++ pathname reader. Drop the mapping before deleting or renaming that source; this was not verified and should be tested in the extraction slice.
