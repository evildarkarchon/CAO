# #465 Assess C++ test coverage for scenario porting [CLOSED]

## Question

Do CAO's C++ tests cover enough behaviour to be worth porting as Rust test scenarios, in addition to the differential corpus?

The parity oracle is a differential corpus (C++ oracle vs Rust on generated mod trees). C++ scenarios are ported as Rust tests too, but only if coverage justifies it. There are about 450 QtTest cases in `tests/`, mostly white-box through internal C++ seams (`RunWorkService`, `TemporaryArtifactRegistry`, and others).

Produce a coverage assessment:

1. Map the test suites to the parity contract: GLOSSARY concepts, ADR-0001 and ADR-0002, the staging-ownership invariants, and the `.scratch/*/spec.md` invariants. Mark which invariants are well covered, thinly covered, or uncovered.
2. Classify each suite as portable as a scenario (it states an observable invariant) or implementation-bound (it tests a C++ seam that won't exist in Rust).
3. If available, measure line or branch coverage. For example, use the `ninja-linux` preset's coverage option, or OpenCppCoverage on Windows. If measuring isn't practical, say why.
4. Recommend porting scenarios or relying on the differential corpus alone, with the threshold you used. If porting, list which suites to port.


--- comment by evildarkarchon
## Resolution

**Recommendation:** port C++ test scenarios as Rust tests selectively, in addition to the differential corpus. Don't rely on the corpus alone.

The safety-critical invariants are well covered in C++, but almost all of those tests need fault injection, a cancellation checkpoint, concurrency, or a crash window. A black-box differential corpus can't reach any of those deterministically. Engine output (texture format and compression decisions, mesh optimization, `hkxcmd`, created-archive content) is barely tested in C++, so the corpus is the only oracle there.

**Threshold:** port a suite when both of these hold:

1. At least 25% of its scenarios assert a parity-contract invariant **and** the corpus can't reach them deterministically.
2. Those scenarios make at least one invariant area well covered, meaning at least 3 independent scenarios that assert outcome, evidence, or filesystem state.

Static scenarios become hand-written corpus seeds instead. Suites bound to a C++ library or API shape are dropped.

**Result:** about 235 of 404 test slots (~58%) are contract-bearing and corpus-unreachable. 17 of 27 invariant areas are well covered.

### Coverage by invariant area

- **Well covered:**
  - Run Outcome precedence
  - Run Phase / Phase Skip Reason
  - Run Evidence retention and publication
  - Safety Cleanup
  - Temporary Ownership and staging recovery (15 unverifiable-manifest variants)
  - Staged publication (three-state receipt)
  - Committed Mutation retention under cancel or failure
  - Operation Failure safe-to-continue
  - Archive Precedence and Archive Collision
  - Loose-over-Archived / Effective Asset Tree
  - Dry Run non-mutation
  - Archive Finalization and Loading / Dummy Plugins (ADR-0002)
  - Routing Policy and Skip Reason
  - Mesh Reference Maintenance
  - Mod Selection and Several Mods
  - Run Handle, Start Error, and one active run (ADR-0001)
  - Run Event ordering and GUI close deferral
- **Thin:**
  - Run Progress
  - `CAO-STAGING` versions: v1 has a literal fixture, v3 is covered only as writer output, and **no v2 fixture** exists
  - Empty-directory pruning
  - Profile compatibility: SSE/FO4 `profile.ini` only, **no TES5**, and no `settings.ini` or QSettings list-encoding round-trip
- **Uncovered or near-uncovered:**
  - Texture optimization decisions (4 resize and mipmap rows only)
  - Mesh optimization levels
  - `hkxcmd` animation conversion (always faked)
  - Created-archive content
  - `MainWindow` and dialog enable/disable rules
  - HTML log format

Line and branch coverage were **not measured**. OpenCppCoverage is not installed (installing it was out of bounds). The only build tree (`D:\repos\CAO\build`) is a stale MSVC Debug Ninja build. llvm-cov would need a full clang-cl rebuild of the vcpkg/Qt tree, and the `ninja-linux` `--coverage` preset is GCC/Linux. The research doc gives the follow-up command. The decision rests on whether the corpus can reach each scenario, and percentages don't measure that.

### Suites to port, in priority order

1. DurableStagingTests
2. RunExecutorTests
3. AssetExecutionTests
4. AssetRunTests
5. ArchiveFinalizationTests
6. ArchiveFirstAssetDiscoveryTests (the injected cases)
7. AssetRoutingTests
8. GuiRunTests
9. The Run Handle subset of OptimizationRunServiceTests
10. Selected RunEvidenceTests, MainOptimizerTests, ApplicationRunSetupTests/RunSetupTests, and MeshReferenceMaintenanceTests cases

Port each as a scenario (intent, fixture tree, and assertions) against the Rust seams. Don't transliterate the C++ fixtures.

**Drop:** the CLI suites (CliRunTests, CliExecutionTests, CliConsoleInterruptTests, OptionsCAOTests), ApplicationLoggingTests (plog), and GuiRunDispatchTests and RunEventDeliveryTests (Qt dispatch; re-derive them from ADR-0001).

**Write new tests** that the C++ suites don't have: a v2 manifest literal, TES5 behaviour, the INI round-trip, and the GUI rules on the deviation list.

### Surprises for other tickets

- **#467 equivalence:** no C++ test golden-compares engine output, so the content equivalence rule for DDS, NIF, HKX, and BSA has no precedent.
- **Undocumented behaviours** need a parity decision. The C++ tests pin them, but GLOSSARY, the ADRs, and staging-ownership don't mention them:
  - `.caobad` quarantine
  - free-space preflight
  - Windows-device-name batch blocking
  - `filesToNotPack`
  - per-Mod-Root headparts
- **Differential harness:** the oracle's comparable surface is the CLI `EVENT:` stream plus its exit codes (`docs/cli.md`). The harness must normalize Run IDs, nonces, and paths, and it can't drive cancellation deterministically.
