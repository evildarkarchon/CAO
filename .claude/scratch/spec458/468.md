# #468 Choose the Rust workspace crates and seams [CLOSED]

## Question

Which crates make up the Rust Cargo workspace, and where do the seams sit?

Decide:

- **Crate boundaries.** For example: a domain and run-engine crate (Optimization Run Service, Run Executor, routing, Run Evidence, staging); profile and settings I/O; native adapter crates (the DirectXTex/BC7 path, the nifly shim, `hkxcmd` subprocess, archives over `ba2`); the Slint GUI binary; and the test driver for the differential corpus.
- **Seams.** Which seams are injectable for tests: the Run Scheduler, the asset optimizers, and the filesystem and native file-safety layer.
- **Error model.**
- **Process-wide state:** one active run per process, profile selection, and logging.
- **Where Windows-only code lives.**

Keep it simple: this is a port, not a re-architecture. The existing C++ module split (`src/Run`, `src/AssetRouting`, `src/AssetExecution`, the optimizers) is the default starting point.

## Resolution

The port uses a coarse Cargo workspace of eight crates. A crate boundary exists only where it isolates a slow C/C++ `cc` build, fences off `unsafe` or Win32 code, or is shared by two binaries. Seams are ported one-to-one from C++ as `dyn` traits, with no new ones.

### Layout

- The repo-root `Cargo.toml` is a **virtual workspace**, with members under `crates/`.
- Crates are named `cao-*`, except `nifly-sys`.
- The workspace uses edition 2024.
- The root holds `[patch.crates-io]`, which points `directxtex` at the fork, and `[workspace.dependencies]` pinning the versions already decided.
- CMake ignores `crates/` and Cargo ignores `src/`, so the two trees live side by side, and nothing moves when the C++ is deleted.

### Crates

| Crate | Holds | Native |
|---|---|---|
| `cao-core` | Asset Routing, asset execution, Run Lifecycle, Run Evidence, Run Executor, Optimization Run Service, staging and Temporary Ownership, and the *logic* of archive discovery and finalization. The nine C++ library targets become modules here. | none |
| `cao-winfs` | Every `unsafe` call and `windows-sys` import for file safety: pins, volume identity, durable rename and delete, and MSVC-canonical paths. | windows-sys |
| `cao-profiles` | The QSettings INI port, profile discovery, the options and settings model, and the Qt-free equivalent of OptimizerProfileSnapshot. | none |
| `cao-archive` | The bethutil port over `ba2`: game tables, dummy plugins, `ArchiveData` split and merge, and naming. | ba2 → DirectXTex |
| `nifly-sys` | The C shim, vendored nifly, the `cc` build, and the safe `Nif` wrapper. | C++ |
| `cao-optimizers` | The texture (directxtex fork plus the D3D11 device), mesh, animation (`hkxcmd`) and archive backends. It also holds the **composition root**, which wires production backends, adapters and the profile-backed Run Configuration Provider into a ready Optimization Run Service. | all |
| `cao-gui` (bin) | The Slint app, ported from the prototype. It owns profile selection. | slint, rfd |
| `cao-parity` (bin, never shipped) | The headless differential driver. Its internals stay in the harness fog. | via the composition root |

The composition root must be a library because both binaries need it. If it lived in one binary, the parity driver would exercise different wiring from the app users run.

### Dependency graph

- `cao-winfs`, `cao-profiles`, `cao-archive` and `nifly-sys` are **leaves**, with no workspace dependencies.
- `cao-core` depends only on `cao-winfs`. It reads Archives through an archive-reader trait (list entries, extract an entry) and never depends on `ba2`. Core and its ported tests therefore build without a C++ toolchain.
- `cao-optimizers` depends on everything else. It implements core's traits, adapting leaf types such as archive, profile and nif types into them. It is the only crate that knows how CAO is wired. The orphan rule also forces these adapters to live here.
- `cao-profiles` has no notion of a Run Request. The composition root translates profile and options data into core's `RunRequest`, `RunConfiguration` and per-run optimizer settings, the job OptionsSnapshot and ApplicationRunSetup do in C++.
- `cao-gui` depends on `cao-optimizers`, plus `cao-profiles` to read and write settings. `cao-parity` depends on `cao-optimizers`.

### Seams

Port the C++ seam set exactly, as object-safe traits behind `Box<dyn …>` or `Arc<dyn …>`. No generic type parameters are threaded through the service. Each `std::function` bundle becomes one trait each, or a struct of boxed closures where C++ already uses closures. The seams are:

- Run Scheduler
- Run Work Service
- Safety Cleanup Service
- Run Configuration Provider
- Run Observation Sink and the work milestones
- Asset Execution Backend: one trait over all optimizers, not one per optimizer
- The archive reader, which is new only as a crate boundary; it replaces `ArchiveExtractionOperation` and the archive closures in AssetRunAdapters
- The capacity and volume-identity probes

These are **not** seams: a filesystem abstraction, a clock, and the staging nonce. As in C++, tests reach faults through the seams above plus real temporary directories.

### Error model

- The domain records stay plain data types:
  - `StartError` is returned synchronously from the service.
  - `RunFailure`.
  - `OperationFailure { mutation: MutationState, safe_to_continue, … }`.
  - `RunOutcome`.
- The C++ exception boundaries become `Result` returns at the same places.
- Each library crate's internal errors (I/O, nifly, ba2, INI) are a `thiserror` enum. There is no `anyhow` in libraries; it is allowed only in the two binaries.
- `AssetInitializationCancelled`, which used an exception as control flow, becomes an ordinary `Err` or `Cancelled` variant.

### Panics

The workspace keeps `panic = "unwind"`, and `catch_unwind` sits at the C++ containment boundaries:

- **The asset backend call.** A panic becomes an Operation Failure with `PartialOrUnknown` mutation, unsafe to continue.
- **The Run Worker.** A panic produces a Failed outcome, and Safety Cleanup still runs.

A Run Evidence invariant violation panics only after cleanup, matching C++. The nifly shim never unwinds across FFI, so this policy only concerns Rust panics.

### Threading (clears the "Run Handle and Run Event dispatch" fog)

- The Run Worker is one `std::thread`, started by `StandardRunScheduler`. There is no async runtime.
- The Run Handle's `Drop` requests cancellation and joins the worker. Cancellation uses an `Arc<AtomicBool>` and is checked between Assets. A nifly call in progress can't be interrupted, so the join waits for it, as already accepted.
- The Run Event Dispatcher is a `Box<dyn Fn(RunEvent) + Send>` supplied by the adapter. The GUI's dispatcher forwards through `Weak::upgrade_in_event_loop`. On `EventLoopTerminated` the event is dropped silently, because the window owns the handle and joins it anyway.
- `rayon` is used only inside archive packing and compression, never as the Run Worker.

### Process-wide state

- **One active run per process.** A `static Mutex<Weak<RunShared>>` inside `cao-core`'s service, ported as is.
- **Profile selection.** There is no global singleton. `cao-gui` owns the selected profile, the Run Request carries the profile identity, and the provider re-reads `profile.ini` during Preparing. This removes the thread-unsafe C++ `Profiles` singleton.
- **Logging.** Libraries log through the **`log`** facade macros and hold no logger state; `tracing` was rejected. The binary installs the sink. The sink's design is a separate ticket.
- **COM and the D3D11 device.** Both belong to the texture backend in `cao-optimizers` and are initialized per worker thread, not in `main`.

### Windows-only code and `unsafe`

- Every POSIX `#else` branch is dropped. The crates carry no `cfg(windows)` gates; the workspace is simply Windows-only.
- `unsafe` is allowed only in `cao-winfs`, `nifly-sys`, and the D3D11 device module of `cao-optimizers`. `[workspace.lints]` sets `unsafe_code = "forbid"`; members opt in with `lints.workspace = true`, and the three native locations override it locally.
- `cao-gui` embeds the application manifest (`longPathAware`, UTF-8 `activeCodePage`). Which build-script crate does the embedding is decided in the build-integration ticket.

### Where the ported scenario tests live

| Scenarios | Location |
|---|---|
| Run safety (Run Handle, Run Executor, Safety Cleanup, Archive Precedence, routing), using fakes of the seam traits | `cao-core/tests/` |
| Durable staging and manifest recovery, run against real temporary directories | `cao-core/tests/` |
| `cao-winfs` primitives | unit tests in `cao-winfs` |
| Archive finalization against real archives (Loading Plugins, Dummy Plugin bytes, capacity) | `cao-optimizers/tests/` |
| Pure archive finalization logic, using a fake reader and fake probes | `cao-core/tests/` |
| INI compatibility fixtures | `cao-profiles/tests/` |
| Engine output parity | the differential corpus only, as already decided |

### Rejected

- Mirroring the nine CMake targets one-to-one.
- A single crate.
- `cao-core` depending on `ba2` directly.
- Leaves depending on `cao-core` to implement its traits.
- `panic = "abort"`.
- tokio.
- A `rust/` subdirectory.
- `tracing`.
- New filesystem, clock or nonce seams.
