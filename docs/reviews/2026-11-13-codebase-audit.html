The three high findings

  • CORE-1: converting foo.tga overwrites an existing foo.dds and deletes the TGA, with no collision check anywhere.
  • FFI-1: a Mesh save does not detect write errors, so on a full disk a truncated NIF can be published over the original.
  • FS-1: extracting an Archive rewrites the whole ownership manifest once per entry, which is quadratic I/O and caps extractable Archives near 75,000 entries.

Patterns across the findings

  • One unusual file stops a whole run. A hard-linked file, a NIF that makes nifly throw, an Archive entry with a non-UTF-8 name, or a failed staging bootstrap each end the run or block the Mod Root, although none has changed anything on disk (CORE-2, BE-1, BE-4, FS-3, FS-9). The safety machinery is right to fail closed; these cases fail closed at the wrong scope.
  • Typed errors are reduced to bool or a string where core decides what to do. The backend seam cannot tell "corrupt" from "could not read", so Quarantine renames files for environmental failures and Mesh failures carry no cause (CORE-9, BE-2, BE-16, FS-12).
  • Runs are not idempotent. Unchanged Meshes are re-saved, every Animation is re-sent to the converter, and every Asset is hashed several times, on every run (BE-6, BE-7, CORE-4), with two quadratic costs on large inputs (CORE-3, FS-6).
  • Silent wrong outcomes. An unreadable exclusion list, a plugin named .ESP, an existing profile name or a pinned directory each produce a result the user did not ask for, with no error (GUI-2, BE-3, GUI-1, FS-2, BE-5).
  • C++ parity is now the main source of surprising behaviour. AGENTS.md says parity is history, but many of the findings above trace to a comment that begins "as in C++". About 725 source lines still justify themselves that way (WS-6).
  • A green run depends on the machine. There is no CI, and long-path, symlink and GPU tests pass or are skipped according to host settings (WS-1, WS-2).

What is in good shape

An audit that lists only problems misstates the codebase. These were checked and found sound, and are worth protecting as the findings are worked through.

File safety

  • No path was found that loses or corrupts an original: registration is flushed before creation, staged bytes before the rename, and publication is a native same-volume rename with no copy fallback.
  • Recovery deletes only recorded, pinned, single-link entries by handle, never recursively, and fails closed on anything it cannot prove.
  • The manifest parser is bounded, uses checked arithmetic and rejects traversal, streams and aliases.
  • Size and capacity arithmetic saturates; no truncating cast on an untrusted length was found anywhere.

Unsafe code and parsing

  • unsafe is fenced by lint tables to four crates; all 36 production blocks carry a SAFETY comment that matches the code.
  • Every C++ shim entry point is noexcept with a catch-all, and memory stays with one allocator.
  • The plugin (HDPT) reader bounds-checks every header, caps decompression and cannot loop without progress.
  • hkxcmd is run without a shell, with drained pipes, a timeout, kill and wait.

Design and concurrency

  • Outcome types make "succeeded but unsafe" unrepresentable, and the continue-or-stop rule is written in one place.
  • The run service has no lock inversion and no lost wakeup; two runs cannot be active at once.
  • Panics are contained in layers: provider, work, cleanup, traversal and payload drop.
  • The Application Log documents and follows its lock order, and formats outside the lock.

Profiles, tests and docs

  • The QSettings INI reader and writer matched Qt 5.15's routines on every path walked; saves are atomic and keep unknown keys.
  • Roughly half the workspace is tests, built on shared fakes of core's seams, including crash-child scenarios for staging.
  • Zero clippy warnings, no TODO markers, three justified #[expect]s in production code.
  • The glossary's vocabulary is used consistently in code, and comments explain why, not what.

CORE-1

Converting foo.tga silently replaces an existing foo.dds

Highcorrectnessverifiedfixed

crates/cao-core/src/execution.rs:596 · :698 · crates/cao-core/src/routing.rs:800 · crates/cao-optimizers/src/backend.rs:205

let output = absolute(&if variant == TextureVariant::Convertible {
    path.with_extension("dds")
...
let publication = receipt.publish(&output, PublicationPolicy::Replace);

Why it matters. A mod that ships both a TGA and a DDS of the same name (authors often leave sources in) has both routed. The conversion captures the existing .dds as its publication target, publishes over it with Replace, then deletes the .tga. The backend always reports a conversion as a change ("Conversion always produces a new DDS"), and there is no collision check in routing, the executor or the backend. The DDS the game was actually loading is irreversibly replaced by a re-encode of a file the game never read, and the run reports success.

Suggested change. Decide the rule explicitly and test it. The conservative options are to skip a convertible Texture whose .dds sibling exists (with a Skip Reason the user can see), or to publish conversions with NoReplace so the collision becomes a contained failure.

Confidence: high for the behaviour as read; it was not executed.

Correction. The first version of this card said no test had both files present. That was wrong: conversion_only_work_converts_in_apply_and_only_evaluates_in_dry_run in crates/cao-core/tests/asset_execution.rs wrote an "old destination" DDS beside the TGA and asserted that Apply replaced it. The overwrite was therefore pinned behaviour inherited from the C++ suite, not an untested accident.

Resolution. Fixed in the commit that adds this report. A conversion whose DDS destination is already a file now completes with no mutation, before the backend loads anything, and logs a warning; it is a success, not a failure, so a Mesh that names the TGA can still be pointed at the DDS. A conversion otherwise publishes with NoReplace, so the rename itself refuses a DDS that appears mid-attempt. Dry Run reports the same decision. Three existing tests that assumed the overwrite were updated, and two were added (a_conversion_never_replaces_an_existing_dds, a_dds_that_appears_during_a_conversion_is_kept). One consequence to be aware of: a TGA left behind by a failed source removal is no longer cleaned up by re-running, because its DDS now exists.

CORE-3

The Several Mods overlap check opens directories a quadratic number of times

Mediumperformanceverifiedfixed

crates/cao-core/src/run/mod_selection.rs:229 · :89

for existing in &roots {
    if contains_directory(existing, &resolved).map_err(io_failure)?
        || contains_directory(&resolved, existing).map_err(io_failure)?

Why it matters. Each contains_directory call opens the boundary and every ancestor of the other path to read its identity, and each new child is compared with every root accepted so far, in both directions. For N children at depth d that is on the order of N² × d handle opens. A mods directory with a thousand entries a few levels deep comes to millions of opens during Preparing, before any work starts, with cancellation polled only once per child.

Suggested change. Compute each resolved root's identity and its ancestor-identity chain once, keep one set of root identities and one of ancestor identities, and test each new child against both. That is linear in N × d.

Confidence: high for the complexity; the wall-clock cost was estimated, not measured.

Resolution. Fixed in step 6, as suggested. Each child's identity chain, itself and every ancestor, is read once. The accepted roots are kept in two identity maps, their own identities and every identity in their chains, so each new child is checked against all of them in one pass, linear in N × d. The failure still names the earliest overlapping root, which a new test pins with a non-adjacent pair. Measured on a release build, a Several Mods Dry Run over 1,000 children took 0.27 s against 521 to 552 s on the commit before. The baseline checkout sat six directory levels deeper (24 against 18), which inflates its figure by roughly a third; the difference is still more than three orders of magnitude.

CORE-4

Every Apply Asset is read and hashed several times, even when nothing changes

Mediumperformanceverifiedfixed

crates/cao-core/src/execution.rs:622 · :687 · :855 · :504 · crates/cao-core/src/run/artifacts.rs:812

if !self.backend.save_mesh(&staged) || asset_fingerprint(&staged).is_none() {

Why it matters. The destination snapshot (a full read with a byte-at-a-time FNV-1a loop) is taken for every Texture and Mesh before the backend loads it, so a re-run over an already optimized tree reads every file twice. A changed Asset's original is hashed again at stage and publish, and its output is hashed once more only to learn that it is non-empty. A converted TGA is hashed four times on the success path although the pin's own comment says the bytes cannot change while write sharing is denied. On texture-heavy mods this is a large share of run time spent on I/O that decides nothing.

Suggested change. Replace the asset_fingerprint(..).is_none() non-empty checks with a metadata size check and compute the output fingerprint only when converting. Let PinnedSource::unchanged_at_path compare identity alone. Consider deferring the destination snapshot until the backend reports a change.

Resolution. Fixed in step 6 with the safe cuts. By the owner's decision, the destination snapshot is still taken before the backend loads, since it is what proves the saved bytes came from the file that was read. The non-empty checks on a staged output are now a metadata size check, and an output is hashed only for a conversion. PinnedSource compares identity alone, because its deny-write share mode keeps the bytes from changing. Staging compares the destination's identity and change metadata without hashing it, and publication still compares the whole snapshot, bytes included. A changed Mesh or in-place Texture now hashes its original twice instead of three times and its output not at all. A converted TGA's source is never hashed (four times before). A re-run over unchanged Assets still reads each one twice, the snapshot and the load, as decided. The identical-output check that BE-6 adds reads both files only when their sizes match.

CORE-6

Failed attempts leave their staged sibling registered until Safety Cleanup

Mediumdesignverifiedfixed

crates/cao-core/src/execution.rs:941 · :678 · crates/cao-core/src/run/staging.rs:48

// An unpublished receipt leaves its empty sibling to Safety Cleanup.
const MANIFEST_BYTE_LIMIT: usize = 8 * 1024 * 1024;
const REGISTRATION_LIMIT: usize = 100_000;

Why it matters. Apply stages a durable sibling for every Animation before the converter runs, and a failed or unchanged attempt returns without releasing it; the same holds for a failed Texture or Mesh save. Each leftover is an empty file beside the user's Asset for the rest of the run plus a manifest record, and every later release rewrites a manifest that keeps growing. If the outstanding records reach the registration or byte limit, the next stage fails with StagingError::Invalid, which CORE-2's rule turns into a run-ending failure.

Suggested change. Give PublicationReceipt an explicit abandon step (delete the sibling, release the record) and call it on the failed and unchanged paths, or stage an Animation only once the converter is known to be needed.

Confidence: high for the mechanism; how often it bites depends on how many attempts fail in one Mod Root.

Resolution. Fixed in step 3 of the suggested order, with the explicit abandon step. PublicationReceipt::abandon deletes the staged file through a handle that proves its identity, then releases its manifest record, so a crash between the two leaves a registered, absent name, which cleanup and recovery already skip. The executor calls it on every path that staged and will not publish: a failed or unchanged Animation conversion, a failed Texture or Mesh save, and output that is not a usable file. A publication that fails before its rename abandons its file the same way. If abandoning fails, the file stays owned for Safety Cleanup, as before, and the attempt's result does not change. The Animation outcome tests now check that the sibling and its record are gone before Safety Cleanup runs, and the publication tests that a refused publication leaves only the run child registered.
