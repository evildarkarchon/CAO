1 · Run Request intake leaves the composition root

  • crates/cao-optimizers/tests/composition_root.rs:36–391
Before: the same rules derived in two crates
After: one intake, two callers

Problem. composition.rs is where the options form, the Profile model, core's Run Request and the backend settings meet, so every reshape lands there (41 commits). The rules that turn the form into a Run Request are restated in the window: Admission is built twice, "ratio wins" twice, and "what counts as Mesh work" twice.

Solution. One module turns the options form into a Run Request and answers the window's "is this held back?" question from the same derivation. The composition root keeps only wiring.

  • locality: each form rule stated once
  • Admission built once, not twice
  • ~350 test lines lose app dir and serial()
  • composition root stops absorbing churn
  • leverage: window and run cross one interface

Problem. capacity.rs measures demand well, but the decision about what a shortage does (fail the run, fail one attempt, or warn) is made in five modules. Problem. The Run Toolset is shallow: its five crate-private methods each forward to one free function. The caller chooses between finalize_archives and plan_archive_creation, and the creation prologue is copied between the planning path and the doing path.

4 · One read of the Selected Profile

Worth exploringin-process
  • crates/cao-optimizers/src/composition.rs:267–347, 496, 504, 558–573
  • crates/cao-optimizers/src/profile.rs:28–112
  • crates/cao-core/src/run/preparation.rs:37
  • crates/cao-profiles/src/settings.rs
Before: the Selected Profile is split in two halves
After

Problem. The glossary's one Selected Profile is two values in the code. The backend's half keeps raw ProfileSettings and derives the Texture Target and Mesh Target late, inside create. Following any one profile fact takes 4–6 files across 3 crates, and a unit test rebuilds the private half by hand.

Solution. profile.rs reads a Profile once into the whole Selected Profile, both halves, with every fact derived at read time. read_profile, its fallback policy and PreparedProfile move out of the composition root.

  • locality: profile mapping in one module
  • a malformed target fails at read, not create
  • testable without starting a run
  • hand-built test fixture deleted

Problem. Slint properties are the window's source of truth, and the typed models are rebuilt from them on every save. The rules read Slint directly, and tab enabling keeps its own capability table beside rules.rs. As a result, rule behaviour can only be tested through a headless window, and several tests poke properties past the accessible controls.

  • rules tested without a window
  • tabs and Run Request share Admission
  • property pokes leave the tests

Top recommendation

1 · Run Request intake leaves the composition root

The composition root is the repo's most-churned file because it is where four models meet. Lifting the form → Run Request derivation into one module removes rules that are stated in two crates today, turns ~350 lines of heavy harness tests into fast in-process tests, and sets up card 5. It is pure, in-process code with no seam to invent. Card 2 (Capacity Check verdicts) is the close second: it is smaller, and its rules are still fresh from #639.
